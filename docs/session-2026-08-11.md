# Session Summary — Bedrock Live Verification + Credential Refresh Tooling

**Date**: 2026-08-11

Deployed the Phase 2/3 multi-backend work to production and got `aws-bedrock` working
end-to-end.

## What was done

- Committed and pushed the Phase 2/3 work (`0a9b53d`, "feat: multi-backend adapters (Phase 2/3)
  + admin backend switcher"). CI (`deploy` + `publish-npm` jobs) ran green.
- Uploaded real AWS Bedrock STS credentials (`aws-access-key-id`, `aws-secret-access-key`,
  `aws-session-token`, obtained via `stax2aws` profile `stax-au1-telstra-agentic-framework`,
  account `669076482267`) to Key Vault `kv-aicoach-rits`, wired as Key Vault references in
  `infra/main.tf` (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN`), plus
  `AWS_REGION`/`AWS_BEDROCK_MODEL_ID` app settings (model:
  `au.anthropic.claude-haiku-4-5-20251001-v1:0`, a cross-region inference profile — raw model
  IDs fail with on-demand throughput errors). `terraform apply`'d successfully.
- Azure App Service didn't pick up the new container image immediately after CI pushed to ACR
  (webhook/polling propagation delay) — required a manual container restart before `/admin`
  (new route) started responding.
- Switched the live backend to `aws-bedrock` via the new `/admin` UI; `/health` confirmed the
  switch took effect.
- First test `POST /v1/chat/completions` call failed with `ResourceNotFoundException: Model use
  case details have not been submitted for this account` — an AWS Bedrock account-level
  requirement (separate from IAM/model-access approval) to fill out an "Anthropic use case
  details" form before invoking Claude models. Not a code or credentials issue — the adapter
  correctly caught and surfaced the SDK error as a 502 `bedrock_error`.
- After the use-case form was submitted, added `infra/refresh-bedrock-creds.sh` — a script that
  runs `stax2aws login -p stax-au1-telstra-agentic-framework -f`, reads the fresh STS
  credentials via `aws configure get ... --profile`, uploads them to Key Vault
  (`az keyvault secret set` x3), then restarts the `llm-aiproxy` Web App
  (`az webapp restart`). Ran it to rule out stale credentials as the cause.
- Retested after the credential refresh — same use-case-form error persisted immediately, but a
  retest a short while later (after AWS's ~15 minute propagation window) **succeeded** — Bedrock
  chat completions now work end-to-end in production with the `claude-haiku-4.5` model.
- Confirmed no changes needed on the AItutor client side: it only calls
  `POST /v1/chat/completions`, and every backend (including `aws-bedrock`) is normalized to the
  standard OpenAI response shape by the adapter layer. Flagged two conditional caveats for
  AItutor if it ever changes usage: (1) `aws-bedrock`'s native adapter returns `501` for
  `/v1/embeddings` (not supported), and (2) native-adapter streaming via the Anthropic-format
  `/v1/messages` endpoint is single-chunk, not true token-by-token (only relevant if AItutor
  switches to that endpoint).

## Known gaps / open items (carried forward)

- No auth on `/admin` — still open, anyone reaching the proxy can switch backends.
- `aws-bedrock` adapter is Claude-only (shares the Anthropic Messages format code path).
- Native-adapter streaming for `/v1/messages` isn't real token-by-token streaming (single SSE
  chunk); `/v1/chat/completions` streaming for native adapters *is* real token-by-token.
- Bedrock STS credentials are temporary (~8h) — re-run `infra/refresh-bedrock-creds.sh`
  whenever Bedrock calls start failing with credential/auth errors.
- `azure-openai` backend has not yet been smoke-tested end-to-end.
